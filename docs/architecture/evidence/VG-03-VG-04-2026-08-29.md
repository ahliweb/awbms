## 3. VG-04 — HTTP/runtime lifecycle evidence

The verification crate uses `#![forbid(unsafe_code)]` and exercises the selected Axum/Tower/Tokio stack.

Automated evidence:

1. `request_id_is_added_and_propagated` — PASS.
   - proves the Tower request-ID layer composes with the Axum router;
   - the same router also carries an explicit 1 MiB request-body limit and a 5-second timeout.
2. `graceful_shutdown_completes_without_aborting_the_server_task` — PASS.
   - binds a real Tokio TCP listener;
   - starts `axum::serve`;
   - signals shutdown through a bounded Tokio channel;
   - verifies the server future exits cleanly within the test deadline.

These tests establish architecture fit for the request lifecycle and graceful-shutdown assumptions. They are not load tests and make no latency/throughput claim.

## 4. VG-04 — PostgreSQL / SQLx / tenant isolation evidence

Database image used by the final run: PostgreSQL `18.6`.

The fixture creates `awbms_app_vg04` with:

- `NOSUPERUSER`;
- `NOCREATEDB`;
- `NOCREATEROLE`;
- `NOINHERIT`;
- `NOBYPASSRLS`;
- no table ownership;
- only the DML/sequence privileges required by the probe.

The probe table has both:

- `ENABLE ROW LEVEL SECURITY`;
- `FORCE ROW LEVEL SECURITY`.

The SQLx transaction wrapper sets tenant context using a bound parameter:

```sql
SELECT set_config('app.current_tenant_id', $1, true)
```

The integration test `postgres_force_rls_is_real_and_tenant_context_does_not_leak` passed and establishes all of the following:

1. the runtime role is not superuser;
2. the runtime role cannot bypass RLS;
3. the runtime role does not own the table;
4. missing tenant context returns no tenant rows (fail closed);
5. tenant A sees only tenant A;
6. tenant B sees only tenant B;
7. tenant A attempting to insert tenant B data is rejected by PostgreSQL with SQLSTATE `42501`;
8. transaction-local tenant context does not leak back into the pooled connection after rollback.

The PostgreSQL service log independently records the expected failed cross-tenant operation:

```text
ERROR: new row violates row-level security policy for table "awbms_vg04_probe"
STATEMENT: INSERT INTO awbms_vg04_probe (tenant_id, payload) VALUES ($1, $2)
```

This is database enforcement evidence, not a mocked authorization response.

## 5. Architecture decision impact

The spike found no blocker that requires changing the Stage-0 selections of:

- Tokio as the async runtime;
- Axum + Tower for HTTP/middleware composition;
- PostgreSQL as authoritative state;
- SQLx as the primary PostgreSQL access layer;
- transaction-local tenant context;
- least-privilege application roles plus `FORCE RLS`.

`AD-04` and `AD-06` may therefore remain in force for Stage 1.

## 6. What this gate does NOT establish

`VG-04 PASS` is deliberately narrow. It does **not** establish:

- production readiness;
- full authentication/session behavior;
- RBAC/ABAC/SoD correctness;
- AWCMS parity (`VG-05`);
- performance or SLO attainment (`VG-09`);
- recovery/rollback capability (`VG-12`);
- production PostgreSQL configuration;
- standards/regulatory compliance.

Those remain separate lifecycle evidence obligations.
